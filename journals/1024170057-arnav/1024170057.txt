WEEK 1: Architecture, tech stack and backend planning

We had the kickoff meeting with the whole group: Harshit Goyal (group leader, ML), Jasmandeep Sharma (Member 4, AML and intelligence layer), Dikshit Gupta (frontend) and me on backend and security. In the rest of this journal I refer to them as the ML, AML and frontend teammates.

I compared a few backend frameworks and went with FastAPI, mainly because it handles async natively, generates Swagger/ReDoc docs on its own, and has Pydantic validation built in. PostgreSQL is the main database for transactions, audit trails and investigation data.

We defined four roles:
- CUSTOMER: submits transactions, sees only their own history
- ANALYST: reviews flagged transactions, manages alerts, opens and investigates cases
- COMPLIANCE: audits platform activity, checks AML thresholds, reviews case resolutions
- ADMIN: monitors system health, manages roles, checks model configs

Set up the folder structure (routers/, services/, models.py, schemas.py, deps.py, config.py, security.py, audit.py), created the venv and started requirements.txt with FastAPI, Uvicorn, SQLAlchemy, Pydantic, Passlib and Python-Jose.

I talked to the ML teammate (PaySim models) and the AML teammate (AML rules, behavior and graph logic) and we agreed to keep their code behind an adapter layer so it stays separate from the API routes.


WEEK 2: Database schema

Went through the PaySim features with my teammates and worked out what the schema needs for both the ML models and AML detection. Wrote the SQLAlchemy models in app/models.py:
- User: credentials, hashed password, role, contact info, active flag
- Transaction: PaySim fields (step, txn_type, balances) plus name_orig, name_dest, currency and timestamp for the AML side
- RiskResult: ML fraud score, AML sub-scores (rule, behavior, network), SHAP features, final hybrid score
- Alert: status (OPEN, IN_REVIEW, CLOSED) and priority
- Case and CaseNote: investigations linked to transactions and alerts
- AuditLog: user actions, IPs, timestamps

Added foreign keys, cascade deletes, and indexes on txn_ref, username, name_orig, name_dest and created_at. app/database.py has the engine, connection pooling and create_all() on startup.

Design choice: I kept PaySim and AML fields in a single Transaction table instead of two, so real-time screening doesn't need extra joins. Tested on local PostgreSQL.


WEEK 3: Authentication and RBAC

Wrote app/security.py with bcrypt hashing through Passlib and JWT creation/validation (python-jose, HS256, expiry from ACCESS_TOKEN_EXPIRE_MINUTES). In app/deps.py I added get_current_user, which decodes the bearer token, and require_roles, which restricts endpoints by role.

Auth endpoints (app/routers/auth.py): POST /api/auth/register, POST /api/auth/login (OAuth2 password flow, returns the JWT) and GET /api/auth/me. Login successes and failures are written to the audit log.

While testing I found that sending role="ADMIN" to /register actually created an admin. Fixed it by forcing every self-registered user to CUSTOMER.


WEEK 4: Transaction APIs and schemas

Built app/routers/transactions.py: POST /api/transactions (submit and screen), GET /api/transactions (list with pagination and filters) and GET /api/transactions/{id} (details with risk results). Schemas in app/schemas.py are TransactionCreate, TransactionRead and TransactionFilter.

Each transaction gets a unique txn_ref (UUID prefix) and a UTC timestamp. For privacy, a CUSTOMER's list query is limited to submitted_by_id == current_user.id, while ANALYST, COMPLIANCE and ADMIN can search everything. Filtering is by transaction type and date range.

Balance validation rejects negative balances and zero-amount transfers before they reach the database.


WEEK 5: PaySim ML adapter

The ML teammate gave me the trained files: paysim_logistic_regression.pkl, paysim_random_forest.pkl, paysim_xgboost.pkl and paysim_scaler.pkl. I wrote the adapter in app/services/ml_service.py so I wouldn't need to touch the training code.

I read paysim_scaler.feature_names_in_ to get the exact 18 features and their order, then wrote build_features() to compute them at request time: origin and destination balance changes, origin and destination errors, the two amount-to-balance ratios, and one-hot transaction types.

The first version gave normal payments a fraud score of about 0.46, which made no sense. After comparing against the scaler means, I saw that the Random Forest and XGBoost split thresholds were in raw units (like amount < 454881.65), so scaling the input was breaking them. Fix: tree models get raw features, Logistic Regression gets scaled ones. A TRANSFER that empties the whole account now scores about 1.00.


WEEK 6: Case management and alert triage

While the others worked on the AML dataset and rules, I built the investigation side (app/routers/alerts.py and cases.py):
- GET /api/alerts, filterable by risk level and status
- PATCH /api/alerts/{id}/status for triage
- POST /api/cases to open a case linked to a transaction and alert
- GET /api/cases and /api/cases/{id}
- PATCH /api/cases/{id} for status (OPEN, IN_PROGRESS, CLOSED), priority and resolution summary
- POST /api/cases/{id}/notes, so several investigators can add timestamped notes without overwriting each other

Added a constraint so one alert can't end up with duplicate cases.


WEEK 7: Audit logging and analytics

Wrote app/audit.py as an append-only audit trail for compliance. It logs logins (success and failure), transaction submissions, risk evaluations, alert updates, case changes and role changes, with actor ID, username, action, entity type and ID, metadata JSON and client IP.

GET /api/analytics/summary feeds the dashboard: total transactions, volume, alerts by risk level, open vs closed cases. I used func.count() and group_by so the database does the aggregation instead of loading large result sets into memory.

After checking in on how the AML behavior analysis was going, I added indexes on name_orig and timestamp so sender history can be fetched fast.


WEEK 8: Admin APIs

Built app/routers/admin.py:
- GET /api/admin/users (admin only)
- PATCH /api/admin/users/{id}/role
- GET /api/admin/audit-logs, searchable by action and date range
- GET /api/admin/aml-rules, showing active thresholds
- GET /api/admin/ml-models, showing loaded models and config

Role changes are validated against the four allowed roles, and an admin can't deactivate or demote their own account. I also talked through the AML graph logic and combined score with the AML teammate and prepared the DB fields to store the rule, behavior and network scores.


WEEK 9: SHAP explanations

Synced with the ML teammate on the SHAP work for XGBoost, then added TreeExplainer to ml_service.py to compute per-transaction feature contributions. The top features and base value are saved as JSON (shap_top_features, shap_base_value) in risk_results, and GET /api/transactions/{id}/explanation serves them to the frontend.

If SHAP fails, the transaction is still saved and scored. On a single row it ran fast enough that I didn't notice any slowdown in the API.


WEEK 10: Integrating the AML pipeline

Plugged the AML teammate's module into the backend. That part covers the AMLSim data, rule engine, behavior analysis, scoring, graph logic and notification payloads. In app/services/aml_service.py I add code/ml to sys.path and import it dynamically, so there's no copied code and the original package structure (src.analysis_aml, src.rules_aml, src.notifications_aml) stays untouched.

I mapped our DB fields to the module's parameters (name_orig -> sender_id, name_dest -> receiver_id, txn_type -> payment_type) and wrote queries that fetch the sender's previous transactions (up to AML_HISTORY_LIMIT) and pass them as transaction_history. Without this, the behavior analysis treated every sender as new.

Bug worth noting: the rule engine's parser only accepts %Y/%m/%d %H:%M. I was passing ISO timestamps and the time-window rules were being skipped with no error at all. I now format timestamps the way the module expects.

Results (aml_score, rule/behavior/network scores, triggered_rules, reasons, investigation_summary) are stored in risk_results, with a field for the notification payload. Tested the full flow through the API and transactions now go through both ML and AML.


WEEK 11: Hybrid scoring and tests

With the ML and AML teammates I worked out the hybrid scoring in app/risk.py. The problem: if ML says 0.90 and AML says 0.05 (no history yet), a plain weighted average gives about 0.56 and dilutes the ML signal. Our rule: if either score is below 0.40, take max(ml, aml). If both are 0.40 or above, use 0.6 * ml + 0.4 * aml. Tiers are HIGH (>= 0.70), MEDIUM (0.40-0.69), LOW (< 0.40). MEDIUM and HIGH transactions automatically create an OPEN alert with the triggered rules and ML probability. If the ML models or AML module is down, scoring falls back to whichever score is available.

Tests (pytest + TestClient, in code/backend/tests/):
- test_api.py: auth, RBAC, transaction submission
- test_backend_integration.py: ingestion, ML, AML rules, alert generation
- test_member3_workflow.py: suspicious transaction -> alert -> case -> note -> resolution

They run on a separate SQLite fixture (fresh_database), so the PostgreSQL dev data is untouched. Also wrote seed.py for the demo accounts (admin, analyst, officer, customer).


WEEK 12: Frontend integration and final deliverables

Worked with the frontend teammate on connecting the frontend: CORSMiddleware in FastAPI, and the Vite proxy in vite.config.js so the React app can reach http://127.0.0.1:8000. Fixed a few field name mismatches between the frontend forms and the Pydantic models that were breaking transaction submission.

Added a /health endpoint in main.py showing PostgreSQL status, whether the model pickles loaded, whether the AML module imported, and the current scoring weights and thresholds. Wrote demo.py, which logs in, submits normal and suspicious transactions, checks the SHAP explanation, opens a case and prints the audit trail.

Also checked /docs and /redoc, wrote the backend and database sections of the final report, removed unused dependencies and finished the backend README.
