## WEEK 2 – Database Architecture and Relational Schema Modeling

### Work Done:
- Designed the relational persistence layer in PostgreSQL using the SQLAlchemy Object Relational Mapper (ORM).
- Modeled the core application entities in `app/models.py`:
  - `User`: Account credentials, contact details, assigned system role and active status.
  - `Transaction`: PaySim numerical balance attributes, currency, transaction type, timestamps and sender/receiver identifiers.
  - `RiskResult`: Outputs from ML models, AML sub-scores, SHAP top features, hybrid risk score and categorical risk level.
  - `Alert`: Automated detection records flagged for non-low risk transactions.
  - `Case` and `CaseNote`: Collaborative investigation files, status tracking and timestamped investigator notes.
  - `AuditLog`: Immutable activity log recording security, financial and administrative actions.
- Established relational mappings, foreign key constraints and cascading rules between transactions, risk results, alerts and cases.
- Added database indexes on frequently queried fields (`username`, `txn_ref`, `name_orig`, `name_dest`, `action`, `created_at`).
- Configured application database initialization using `Base.metadata.create_all()` in `app/database.py`.

### Outcome:
The complete relational schema and SQLAlchemy data access layer were developed and tested to support transaction tracking, user access management and investigation lifecycles.

## WEEK 5 – PaySim Machine Learning Adapter and Feature Engineering Pipeline

### Work Done:
- Examined the trained PaySim machine learning model files provided by the ML team member (`paysim_logistic_regression.pkl`, `paysim_random_forest.pkl`, `paysim_xgboost.pkl` and `paysim_scaler.pkl`).
- Developed the ML service adapter in `app/services/ml_service.py` to interface with the saved models without modifying the original training artifacts.
- Extracted the exact 18-feature ordering and feature names required by the models from `paysim_scaler.feature_names_in_`.
- Built the real-time feature derivation function `build_features()` to compute required features from incoming transaction data:
  - `origin_balance_change` (`oldbalanceOrg - newbalanceOrig`)
  - `destination_balance_change` (`newbalanceDest - oldbalanceDest`)
  - `origin_error` (`newbalanceOrig + amount - oldbalanceOrg`)
  - `destination_error` (`oldbalanceDest + amount - newbalanceDest`)
  - `amount_to_origin_balance` and `amount_to_destination_balance`
  - One-hot encoded transaction types (`type_CASH_IN` through `type_TRANSFER`)
- Addressed model scaling differences: passed unscaled raw features to Random Forest and XGBoost (whose tree splits rely on amount units) and standard-scaled features to Logistic Regression.
- Verified prediction probabilities against standard PaySim transaction patterns, including account-emptying transfers, full-balance cash-outs and routine payments.

### Outcome:
A robust machine learning adapter was built to dynamically generate the required 18 features and run real-time fraud inference across multiple model architectures.

## WEEK 8 – Hybrid Risk Scoring Engine and Automated Alert Generation

### Work Done:
- Developed the hybrid risk scoring engine in `app/risk.py` combining PaySim machine learning fraud probabilities and AML analysis scores.
- Implemented the conditional scoring algorithm:
  - When either the ML fraud score or AML score is below 0.40, the system selects the maximum score (`max(ml_score, aml_score)`) to ensure that low risk in one component does not dilute a high detection signal in the other.
  - When both scores reach or exceed 0.40, the system calculates a weighted average (`0.6 * ml_fraud_score + 0.4 * aml_score`).
  - Gracefully handles missing scores if one module is unavailable.
- Configured the platform risk tier categorization:
  - `HIGH`: Final score >= 0.70
  - `MEDIUM`: Final score >= 0.40 and < 0.70
  - `LOW`: Final score < 0.40
- Implemented automated alert creation: transactions evaluated as `MEDIUM` or `HIGH` risk automatically generate an `Alert` entry in `OPEN` status with supporting risk notes.
- Recorded full risk breakdowns and alert associations in the database.

### Outcome:
The hybrid risk engine was finalized and connected to the transaction submission pipeline, automatically classifying transaction risk and raising alerts for suspicious activities.
