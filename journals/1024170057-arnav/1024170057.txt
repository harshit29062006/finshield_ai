WEEK 5: PaySim Machine Learning Adapter & Dynamic Feature Engineering
================================================================================

What I Worked On:
- Received the saved PaySim model pickle files (`paysim_logistic_regression.pkl`, `paysim_random_forest.pkl`, `paysim_xgboost.pkl`, `paysim_scaler.pkl`) from Harshit following his model training.
- Developed the machine learning adapter prototype in `app/services/ml_service.py` to interface with the saved models without modifying training code.
- Inspected `paysim_scaler.feature_names_in_` to extract the exact 18 feature names and column order required by the models.
- Built the real-time feature transformation function `build_features()`:
  * `origin_balance_change = oldbalanceOrg - newbalanceOrig`
  * `destination_balance_change = newbalanceDest - oldbalanceDest`
  * `origin_error = newbalanceOrig + amount - oldbalanceOrg`
  * `destination_error = oldbalanceDest + amount - newbalanceDest`
  * `amount_to_origin_balance` and `amount_to_destination_balance`
  * One-hot encoded transaction types (`type_CASH_IN` through `type_TRANSFER`)
- Solved model input discrepancy:
  * Discovered that Random Forest and XGBoost tree split thresholds were in raw amount units (e.g., `amount < 454881.65`), so scaling them caused normal payments to show elevated fraud scores (~0.46).
  * Ensured tree models receive raw features while Logistic Regression receives standard-scaled features.
- Verified test predictions against known fraud patterns (e.g., full-balance TRANSFER emptying an account correctly yielded ~1.00 fraud probability).

Challenges & Technical Decisions:
- Identifying why unscaled inputs were required for the tree models took careful debugging against the scaler means, but it ensured accurate model inference.

Weekly Summary:
Built an ML service adapter that dynamically constructs 18 features and executes fraud inference across multiple model architectures.

WEEK 11: Hybrid Risk Scoring Engine & Automated System Testing
================================================================================

What I Worked On:
- Collaborated with Harshit and Jasman to implement the conditional hybrid risk scoring algorithm in `app/risk.py`:
  * Solved the score dilution issue: if Harshit's ML model indicates high fraud (0.90) but Jasman's AML module has no historical pattern yet (0.05), a basic weighted average dilutes the score to ~0.56.
  * Implemented the conditional rule: if either score is below 0.40, take the maximum (`max(ml_score, aml_score)`) so a strong signal from either side is never diluted.
  * If both scores reach or exceed 0.40, calculate the weighted average: `0.6 * ml_fraud_score + 0.4 * aml_score`.
- Configured risk tier classification: `HIGH` (>= 0.70), `MEDIUM` (0.40 - 0.69), `LOW` (< 0.40).
- Programmed automated alert generation: transactions categorized as `MEDIUM` or `HIGH` automatically trigger an `Alert` record with status `OPEN` and include Jasman's triggered rules and Harshit's ML probability.
- Developed automated test suites in `code/backend/tests/` using `pytest` and `TestClient`:

- Configured isolated SQLite test database fixtures (`fresh_database`) so automated tests run cleanly without modifying PostgreSQL development data.
- Created `seed.py` to populate initial demo accounts (`admin`, `analyst`, `officer`, `customer`).

Challenges & Technical Decisions:
