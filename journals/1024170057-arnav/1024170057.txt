WEEK 5: PaySim ML Adapter and Feature Engineering
================================================================================

What I did:
- Got the saved PaySim model files (paysim_logistic_regression.pkl, paysim_random_forest.pkl, paysim_xgboost.pkl, paysim_scaler.pkl) from Harshit after he finished training.
- Wrote a first version of the ML adapter in app/services/ml_service.py so I could use the models without touching the training code.
- Checked paysim_scaler.feature_names_in_ to get the exact 18 feature names and their order.
- Wrote build_features() to create the features in real time:
  * origin_balance_change = oldbalanceOrg - newbalanceOrig
  * destination_balance_change = newbalanceDest - oldbalanceDest
  * origin_error = newbalanceOrig + amount - oldbalanceOrg
  * destination_error = oldbalanceDest + amount - newbalanceDest
  * amount_to_origin_balance and amount_to_destination_balance
  * one-hot encoded transaction types (type_CASH_IN to type_TRANSFER)
- Fixed an input problem with the models:
  * Random Forest and XGBoost had split thresholds in raw amount units (like amount < 454881.65), so when I scaled the input, normal payments got fraud scores around 0.46.
  * So now the tree models get raw features and Logistic Regression gets standard-scaled features.
- Tested with known fraud patterns. For example, a TRANSFER that empties the full account gave about 1.00 fraud probability, which is correct.

Challenges / decisions:
- It took some careful debugging against the scaler means to understand why the tree models needed unscaled input, but it made the predictions accurate.

Summary:
The ML adapter now builds all 18 features on the fly and runs fraud prediction across the different model types.

WEEK 11: Hybrid Risk Scoring and Automated Testing
================================================================================

What I did:
- Worked with Harshit and Jasman on the conditional hybrid risk scoring in app/risk.py:
  * We hit a score dilution problem: if the ML model says high fraud (0.90) but the AML module has no history pattern yet (0.05), a normal weighted average brings it down to about 0.56.
  * The fix: if either score is below 0.40, use the max (max(ml_score, aml_score)) so a strong signal from either side isn't watered down.
  * If both scores are 0.40 or above, use the weighted average: 0.6 * ml_fraud_score + 0.4 * aml_score.
- Set the risk tiers: HIGH (>= 0.70), MEDIUM (0.40 to 0.69), LOW (< 0.40).
- Added automatic alert creation: any MEDIUM or HIGH transaction creates an OPEN Alert that includes the triggered rules and the ML probability.
- Wrote automated tests in code/backend/tests/ using pytest and TestClient:
  * test_api.py: authentication, RBAC permissions and transaction submission.

  * test_member3_workflow.py: the whole investigation lifecycle, from suspicious transaction to alert, case creation, adding a note and resolving the case.
- Set up separate SQLite test database fixtures (fresh_database) so tests run cleanly without touching the PostgreSQL development data.
- Wrote seed.py to create the demo accounts (admin, analyst, officer, customer).

Challenges / decisions:
- Added fallback handling in the scoring engine so that if either the ML models or the AML module is temporarily down, the system uses the available score instead of crashing.
